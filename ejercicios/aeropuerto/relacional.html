Modelo relacional

Esquema lógico con tipos, llaves y restricciones.

Ver enunciado del ejercicio

Una aerolínea que opera en varios aeropuertos de Colombia necesita una base de datos para su operación.

  • Cada BASE (aeropuerto donde la aerolínea tiene operación) se identifica con un código IATA de tres letras y tiene nombre, ciudad y país.
  • Cada PILOTO tiene identificación, nombre, número de licencia, horas de vuelo acumuladas y uno o varios teléfonos. Está asignado a exactamente una base.
  • Cada AVIÓN se identifica por su matrícula y tiene modelo, fabricante y capacidad. Permanece en una base.
  • Un VUELO tiene un identificador, un código comercial (por ejemplo AV101), fecha, hora de salida y destino. Sale de una base y lo opera un único avión.
  • En cada vuelo trabajan uno o más pilotos con un rol (capitán o copiloto), y un piloto puede tripular muchos vuelos.
  • Los PASAJEROS se registran con identificación, nombre (nombres y apellidos), fecha de nacimiento y correo; su edad se calcula. Un pasajero reserva vuelos y en cada reserva se guarda el asiento y la clase.

Entidades del enunciado: Piloto, Pasajero y Base. Entidades inventadas para completar el problema: Avión y Vuelo.

Cada flecha va de una llave foránea a la llave primaria que referencia. PK llave primaria · FK llave foránea · UQ única (en VUELO, codigo + fecha forman juntas una llave única).

Esquema

BASE(codigo_base, nombre, ciudad, pais)
PERSONA(documento, nombres, apellidos, fecha_nacimiento)
TELEFONO_PERSONA(documento, telefono)
PILOTO(documento, licencia, horas_vuelo, codigo_base)
PASAJERO(documento, correo, millas)
AVION(matricula, modelo, fabricante, codigo_base)
AVION_COMERCIAL(matricula, num_asientos)
AVION_CARGA(matricula, capacidad_kg)
VUELO(id_vuelo, codigo, fecha, hora_salida, destino, matricula, codigo_base_origen)
TRIPULA(documento, id_vuelo, rol)
RESERVA(documento, id_vuelo, asiento, clase)

Convención: subrayado = llave primaria · azul = llave foránea.

Restricciones de integridad

TablaLlave primariaLlaves foráneasOtras restricciones
BASEPK(codigo_base)——
PERSONAPK(documento)——
TELEFONO_PERSONAPK(documento, telefono)documento → PERSONA (ON DELETE CASCADE)—
PILOTOPK(documento)documento → PERSONA (CASCADE)
codigo_base → BASE		UNIQUE(licencia), CHECK(horas_vuelo ≥ 0)
PASAJEROPK(documento)documento → PERSONA (CASCADE)UNIQUE(correo), CHECK(millas ≥ 0), DEFAULT millas = 0
AVIONPK(matricula)codigo_base → BASE—
AVION_COMERCIALPK(matricula)matricula → AVION (CASCADE)CHECK(num_asientos > 0)
AVION_CARGAPK(matricula)matricula → AVION (CASCADE)CHECK(capacidad_kg > 0)
VUELOPK(id_vuelo)matricula → AVION
codigo_base_origen → BASE		UNIQUE(codigo, fecha)
TRIPULAPK(documento, id_vuelo)documento → PILOTO
id_vuelo → VUELO (CASCADE)		CHECK(rol IN ('CAPITAN','COPILOTO'))
RESERVAPK(documento, id_vuelo)documento → PASAJERO
id_vuelo → VUELO (CASCADE)		UNIQUE(id_vuelo, asiento), CHECK(clase IN ('ECONOMICA','EJECUTIVA'))
  • Integridad de entidad: ninguna llave primaria acepta NULL ni valores repetidos.
  • Integridad referencial: cada FK debe existir en la tabla referenciada. Las subclases y los teléfonos usan ON DELETE CASCADE: si se borra la persona o el avión, se borran sus filas dependientes.
  • Dominio: los CHECK limitan rol, clase y valores numéricos.
  • Hay reglas que el modelo relacional no puede garantizar solo con llaves: por ejemplo, que un avión no esté a la vez en AVION_COMERCIAL y AVION_CARGA (disyunción). Eso se controla con triggers o en la aplicación.
